# リプレイ画面の操作と記録条件

[README](../README.md) | [GMOで使う](gmo.md) | [記録仕様](trace-format.md)

## 画面方針

2026-11-15に再設計案A「動画から調べる」を採用しました。左約60%に録画とその下の処理ログ、右約40%に「入出力」「候補」「統合結果」を表示します。淡い背景と白い詳細欄を使い、設定や識別子は折りたたみます。境界をドラッグして幅を調整でき、狭い画面は縦に並びます。[採用したデザイン方針](design-direction.md)を参照してください。

選ばれた処理の行には450msの軽い強調を付けます。OSやブラウザの「動きを減らす」設定ではアニメーションを抑え、選択色で位置を示します。

## 操作

1. 試行の一覧から実験と試行を開きます。開いた後は上部右端の「別の試行を選ぶ」で一覧を開き直せます。同梱のデモ記録では「手元の記録」→ `gmo_model_handover_s301_39328` → `two_arm_handover` を選びます。以下の手順で使う合成デモは `python scripts/make_replay_demo.py --out outputs/geniac_demo` で作り、`--trace-root outputs/geniac_demo/traces --runner-root outputs/geniac_demo/runner` を付けて起動します。
2. 動画下の「ターン」を選び、「再生」を押します。ターン番号は記録された `turn_index` です。「すべて」で試行全体を表示します。
3. 「動画」表示では、動画下に1処理1行の「一覧」を表示します。隣の「APIとPython」を選ぶと、時刻とAPI名、その隣に実行されたPythonを表示します。APIを選ぶと対応場面へ移動して停止し、呼び出し行を強調します。同じ位置のAPIも記録順で個別に選べます。
4. 右の「入出力」には、選んだAPIやPythonの生成元モデルに渡した入力と返った回答を表示します。「一覧」でSAM3やVDM、stdout/stderrなどを選ぶと、その処理の画像・指示・結果や出力を確認できます。マスクはクリックで拡大できます。
5. 「候補」では同じターンの回答を選択欄から1件ずつ表示します。temperatureとエラー・途中打ち切りは選択欄にも表示します。同一入力は一度だけ表示し、「この候補の入力を見る」から参照できます。入力が異なる候補は別入力として表示します。
6. 「統合結果」で同じターンの統合への実送信入力と最終回答を確認します。Python、`REGENERATE`、`FINISH`を区別し、実行コードへの対応が記録されていれば移動できます。
7. 右のタブを切り替えても動画の停止位置・選択中の処理を保ちます。「ターン」の変更や詳細ログ・記録フレームからの処理選択では、右で選んだタブを保ちます。「APIとPython」のAPIやコードを直接選ぶと「入出力」を開きます。再生、手動シーク、「再生設定」内の「2秒巻き戻す」で処理の追従を再開します。再生速度は「再生設定」で変更できます。複数カメラの録画は初期状態で同時に表示し、小さい動画を押すと、位置と選択中の処理を保ってメインのカメラを切り替えます。「全カメラ｜1台」で表示を切り替え、1台表示では「カメラ」から選べます。この表示方法は同じブラウザで記憶します。
8. 動画下の2択ボタン「一覧」「APIとPython」で表示を切り替えます。API表示を使わない場合は「一覧」「処理タイムライン」です。「一覧」が初期設定で、選択は同じブラウザのviewerで記憶します。ブラウザの保存機能（localStorage）が使えなくても切り替えられます。「一覧」では検索・フィルター付きの詳細ログからモデル呼び出し・サービス・標準出力などの記録をたどれます。記録フレームを直接見る場合は「表示」から「記録フレーム」を選びます。

上部の「試行の詳細」には設定・モデル・評価・記録状態をまとめています。同欄の「実行回ごとの表示」で従来のコードブロック単位の表示を開けます。「リプレイを見る」で戻ります。

「一覧」の詳細ログは、種類・名前・ターンや行番号・所要時間・状態・イベント番号を1行にまとめて表示します。行をクリックすると、その処理を選択して引数・戻り値・接続先・HTTP情報・記録フレームなどの詳細を開きます。開いている選択行をもう一度クリックすると閉じます。再生位置への追従や「動画時刻」、API一覧、比較表、`event=` 付きURLから選んだイベントも、自動で詳細を開き、選択行へスクロールします。行はTabキーで移動し、EnterまたはSpaceキーでも開閉できます。

件数の横の「詳細をすべて表示」をオンにすると、すべての行の詳細を表示します。初期設定はオフで、切り替えは同じブラウザのviewerで記憶します。失敗した処理の短いエラー文は、詳細を閉じていても赤字で表示します。隠れている内部呼び出しは親の行に「＋中の呼び出し N件」と表示し、親を開くと字下げした行で確認できます。検索や種類・role・失敗のみの絞り込みも使え、詳細内の検索語に一致した行は自動で開きます。

各画面の上部には共通のパンくずを表示します。評価から開いた試行は「評価一覧 › 変更した部品 › タスク · seed」の順になり、評価名からその評価の比較表へ戻れます。基準の評価名は一覧と同じ「（基準）」付きです。評価に属さない試行や古いログでは「試行を選ぶ › run › 試行」の順で表示します。現在のページ以外はリンクになり、狭い画面では折り返します。

完了した試行をイベント指定なしで開くと、フレーム対応が確認できた後に開始位置の処理を選び、左の強調と右の入出力を揃えます。イベントを指定したURLではその選択を優先し、動画との対応がないイベントには無関係な処理の強調を付けません。実行中の「新しい記録に追従」は最新イベントに追従します。動画を再生・シークすると録画の閲覧へ切り替わり、Liveを再度有効にすると動画を停止します。動画ファイルがまだない実行中の試行では、動画の代わりに各カメラの記録フレームを、記録された順に約3秒遅れで再生します。GMOやRTXからは約2秒ごとにまとめて届くため、最新の1枚だけでなく、その間に保存されたフレームも順に表示します。モデルが考えている間など新しいフレームがなければ最後の1枚で止まり、遅れが10秒を超えたら最新の約3秒前へ進めます。

「別の試行を選ぶ」で開く一覧は、左から「GMO」「手元の記録」「古いログ（トレースなし）」です。GMO連携が有効なら、接続設定が未入力でも最初に「GMO」を開き、一覧から探して「取り込む」→「開く」で表示できます。連携の有効・無効を確認する間は読み込み表示になりますが、「手元の記録」や表示されている「古いログ（トレースなし）」へは確認を待たずに切り替えられます。前回選んだこれらのタブを開き直す場合も、GMOの確認は待ちません。連携が無効なら「手元の記録」を開き、GMOボタンを表示しません。確認でエラーが起きた場合も「手元の記録」を開きますが、「GMO」から設定を読み直せます。選んだタブはピッカーを閉じて開き直しても保ち、ページを再読み込みすると初期選択に戻ります。

「手元の記録」は保存済みのトレース一覧です。「古いログ（トレースなし）」は既存runnerログが1件以上ある場合に表示します。`legacy_run` などのURLで旧形式の試行を開いている場合は、一覧が0件でも表示します。「手元の記録」の「一覧を更新」は古いログの一覧も取得し直すため、最初に0件だった場合や取得に失敗した場合も、保存先の接続やログの追加後に更新すると古いログのタブが現れます。

「入出力」の「記録の詳細」を開くと、デバッグ用の注意帯とイベントの生データを1組表示します。試行一覧の保存先と閲覧専用モードは「一覧の詳細」、旧形式の保存先は「保存先の詳細」で確認できます。各一覧では検索と結果フィルターを使えます。

## 実行中の試行をリアルタイムで見る

GMO B300とRTX PRO 6000 VMを同じviewerで見るには、`bash Start-Replay.sh --from-gmo --rtx` で起動します。評価一覧・評価詳細・試行の上部にある「B300」「RTX」で接続先を切り替えます。RTX用の設定は既定の設定ディレクトリの `rtx.json` から読み、別の場所なら `--rtx /path/to/rtx.json` を指定します。設定ファイルがなければ案内を表示し、B300だけで起動します。RTXの記録は `outputs/rtx/traces` に保存され、接続設定・取り込み・Live追従もサイトごとに独立します。VMにチームで記録を共有するフォルダーがあれば、RTXの設定の `shared_root` にそのフォルダー（例：`~/shared-storage/traces`）を指定します。[接続設定](gmo.md)も参照してください。

「GMO」の「一覧を更新」で実行中の試行を探し、「取り込む」→「開く」を押します。「新しい記録に追従」が有効な間、その試行の変更分を約2秒ごとに取り込み、モデルへの入力と回答、生成されたPython、API呼び出し、出力を自動更新します。通信とコピーの時間に応じて表示は遅れます。リモート側へのインストールやファイルの書き込みは不要です。

実行中は、記録された全カメラの最新画像をカメラ名と「3秒前」などの経過時間付きで表示します。ライブのカメラ画像は赤い枠で囲み、保存済みの動画と見分けられるようにしています。画像はクリックで拡大できます。記録画像は既定で各カメラ約4枚/秒です。増やす場合は、リモートで記録するプログラムの起動時に `CAPX_TRACE_FRAME_FPS=8` などを指定します。保存量と転送量も増えます。MP4は試行が終わって保存されてから通常の動画表示に戻ります。ライブ表示中に試行が終わると、各カメラの残りの記録フレームを再生してから動画に切り替わり、「すぐ動画に切り替える」でも移れます。

ログを選ぶとBrowseになり、リモートの追従更新も止まります。「新しい記録に追従」を再び有効にすると再開します。ページを閉じるか別の試行へ移ると、以前の試行の取り込みは更新要求が途絶えてから30秒以内に止まります。通常の自動取り込み間隔（既定2分）は変わりません。新しい試行は「一覧を更新」ですぐ確認できます。

## 試行の要約を読む

トレースがある試行では、動画とログの上にタスク・seed、達成判定、終わり方、ターン数・書き直し回数・所要時間を表示します。ターンの流れ、最初のエラー、最後のVDMの観察、コードを書くモデルの最後の判断、最後の記録画像も、記録されている項目だけを表示します。「ログで見る」で、その項目のイベントを選びます。モデルの `FINISH` は達成判定とは別に表示します。

終わり方は、太字の原因と数字、その下の短い日本語の説明で表示します。たとえば「ステップ上限に到達（1000/1000 ステップ）」と「ロボットを 1000 ステップ動かした時点で打ち切られました。nut_assembly の公式の上限も 1000 です。」です。試行に実際に適用された上限が残っていなければ「この記録には実際の上限値が残っていません（公式の上限は 1000）」と区別します。公式値はタスクごとの公開ルールから取り、記録の欠けたローカル設定値を補いません。

根拠のフィールド名、規則の出典リンク、不足している記録は、閉じた「根拠を見る」を開くと確認できます。1試行の時間制限、コード実行の時間切れ、ターン・書き直しの上限、未達成の終了宣言、実行エラー、シミュレーターの異常終了、評価ジョブの時間制限、手動停止・置き換え、途中で終わった記録を区別します。書き直し回数だけが分かる過去の試行は「書き直し 10 回で終了（上限の設定は記録なし）」のように表示します。成功・エラー・時間切れなどの大分類は、フィルターや集計の互換性のために残します。「分類は記録から自動で推測したもので、外れることがあります。」という注意も表示します。

モデルが明示的に `FINISH` と答えた場合と、`REGENERATE` がないためパーサーが終了と解釈した場合も区別します。後者は「終了と解釈されたが未達成」（表では「終了扱い」）と表示し、モデルが完了を宣言したとは扱いません。

評価比較の「失敗の内訳」は、時間切れ・打ち切り、未判定、未達成、書き直しの上限、エラー、不明のどのグループでも、具体的な原因・上限ごとの基準／今回の件数と増減を表示します。各原因を開くと、その原因の試行一覧へ進めます。達成判定の「未判定」は成否が記録から分からないことを表し、停止原因が分かる場合は、その原因で内訳をまとめます。

比較表は「ステップ上限」「試行時間」「環境異常」などの短い語を使います。セルのツールチップは、数字を含む原因、短い日本語の説明、「試行を開く」の順です。根拠のフィールド名は表示しません。表の凡例はセルと共通の定義から作り、セルに表示できる語を説明します。実行中は「実行中」です。

評価ページの「公式の評価と条件が違います」には、記録や公開実装で確かめられる違いを、1項目につき短い1文と公開ルールのリンクで示します。対象は、公式にはない1試行の時間制限、成功を判定する時点、時間切れ後の再試行、公式パックと異なる記録済みのステップ上限です。公式は各動作サイクルで一度でも成功すれば成功としますが、ローカル runner はコードブロック終了時だけを調べるため、終了前に状態が崩れると未達成になる場合があります。ローカルの時間切れ再試行は公式の試行返却とは別の仕組みです。3項目を超える分は「ほかの違い」を開くと確認できます。値が記録されていない条件は、同じ条件だったとは判断しません。公開規則の一覧は [stopping-rules.md](stopping-rules.md) を参照してください。

評価に基準があれば、同じタスク・seedの最後の基準試行と比較します。基準に複数の条件があれば同じ条件を優先し、対応を一意に決められなければ比較しません。基準が成功で今回が失敗なら「悪化（基準では成功）」、基準が失敗で今回が成功なら「改善」を表示し、取得できた基準の最後の画像も並べます。複数カメラでは「カメラ」で最後の画像を切り替えます。動画のメインカメラ、記録フレームと同じ選択を使い、基準にも同名のカメラがあれば揃えます。基準にそのカメラがなければ、基準のメインカメラを表示し、その旨を添えます。基準の試行が手元になければ、既存のGMO連携でその1件を取り込みます。トレースのない古いログにはこの要約を表示しません。

## 同じseedの試行を並べる

同じタスク・seedの基準試行があれば、上部バー右側の「基準と並べて比べる」、要約の「基準と並べて見る」、または評価比較表の今回のセルの横にある「並べて見る」ボタンで、`/traces/compare` を開きます。パンくずは「評価一覧 › 評価名 › タスク · seed › 基準と並べて比べる」となり、試行名から今回の試行の要約へ、評価名から評価の比較表へ戻れます。基準と今回のモデル・API・サービス呼び出しと判断をターンごとに並べ、種類と名前が一致する呼び出しの最長共通部分列で対応付けます。追加・削除された呼び出しには片側に空欄を残します。

名前、短い引数の要約、状態、返却内容の要約を比べ、「同じ」「違い」を付けます。最初の差には「ここから違う」とターン・呼び出し名を表示します。バナーは記録された差だけを示し、失敗の原因までは推測しません。「違う行だけ表示」で一致する行を隠せます。各側の呼び出しを押すと、その試行のイベントを開きます。上部の最後の画像も選んだカメラで比較できます。「カメラ」を切り替えると今回と基準に反映し、基準に同じカメラがなければ基準のメインカメラを表示して注記します。画面幅が900px未満では、各行の基準と今回を縦に並べます。

## APIとPythonを同時に追う

動画下の **「APIとPython」** を選ぶと、左に時刻とAPI名、右に実行されたPython全文を表示します。スライダーやキーでシークすると指定時刻で停止し、その時刻のAPIと呼び出し行を表示します。再生中は動画位置に追従します。APIの行をクリックすると、その開始時刻へ移動して停止します。同じ時刻のAPIも記録順で個別に選べます。試行を切り替えても選んだ表示で開き、「一覧」の詳細ログや記録フレームからAPIを選んだ場合も右側のモデル入出力は同じ形で確認できます。

1. 合成デモを開き、動画下の「APIとPython」を選びます。
2. `0.00s` の `goto_pose` をクリックします。動画が停止し、役割の説明とPythonの **3行目** が強調されます。
3. `get_observation` を選んでから `goto_pose` にカーソルを重ねます。説明をプレビューしても、選択や動画の位置は変わりません。
4. 「詳細」でAPI定義の説明・出典と、今回記録された引数・結果・エラーを確認します。
5. `2.00s` のAPIを選ぶと、その場面へ移動して停止します。「← 前」「次 →」で実行順にコードブロックを読みます。長いコードも省略せず、欄内でスクロールできます。
6. 画面右の「入出力」には、そのPythonを生成したモデルへの入力を上、返った回答を下に表示します。「候補」「統合結果」も停止位置を保って開けます。

APIとPythonの対応には `api_call_start.call_site.code_block_id` と1始まりの `line` だけを使います。親子関係・API名・時刻の近さから行を推測しません。行番号が欠ける・範囲外・コード全文が取得できない場合は理由を表示し、行を強調しません。モデル入出力は `code_block_start.source_model_event_id` が示す回答と、そのHTTP要求へ対応付けます。同じターンの別回答や別のHTTP再試行で補いません。

`goto_pose`、`get_observation`、`segment_sam3_text_prompt` は同名APIの参照定義も持ちます。ハンマー受け渡しの7種に加え、競技用の `FrankaControlApiReduced` と `FrankaControlApiReducedSkillLibrary` の登録済みAPIでは、記録されたクラス名・修飾メソッド名に一致する定義を使います。継承されたメソッドも宣言元を照合し、IKによる関節角の計算と関節の移動、左右アーム、カメラ座標とワールド座標を区別して説明します。

「詳細」に定義の原文の抜粋と出典、実行ログに記録された引数・結果・エラーを表示します。未登録APIは「説明未登録」、対応情報の欠落は「未記録」、エラーの原因を特定できない場合は「原因未特定」と表示します。 [ハンマー受け渡しの定義](https://github.com/matsuolab/geniac_prize_2026_code/blob/ac680843fb60c464aa74c87a2815cb5917865be4/capx/integrations/franka/handover_privileged.py) / [競技用の制御API](https://github.com/matsuolab/geniac_prize_2026_code/blob/ac680843fb60c464aa74c87a2815cb5917865be4/capx/integrations/franka/control_reduced.py) / [座標変換などのスキル](https://github.com/matsuolab/geniac_prize_2026_code/blob/ac680843fb60c464aa74c87a2815cb5917865be4/capx/integrations/franka/control_reduced_skill_library.py)

## データの置き方

トレース一式は次の形で置き、`--trace-root /path/to/traces` を指定します。

```text
traces/
└── run-id/
    ├── run.json
    └── episode-id/
        ├── episode.json
        ├── events.jsonl
        ├── payloads/
        ├── assets/
        ├── frames/
        └── videos/
            └── video_combined.mp4
```

トレースがない既存runner記録は次の形で置き、`--runner-root /path/to/runner` を指定します。

```text
runner/
└── run-id/
    ├── run.json
    └── task/
        └── condition/
            └── trial_001/
                ├── video_combined.mp4
                ├── summary.txt
                ├── code.py
                ├── all_responses.json
                ├── ensemble_candidates.txt
                └── ensemble_synthesis.txt
```

各ファイルは保存されているものだけを使います。名前や形式の詳細は[trace-format](trace-format.md#94-episodes-without-a-trace)を参照してください。`--runner-root`へ `trial_001` 自体を指定すると、この階層を探索できません。

MP4のみの動作例は合成デモの「古いログ（トレースなし）」→ `video_only` にあります。同期情報がなくても動画は再生できます。任意のMP4をログへ推測で結び付ける機能はありません。

## 同期と出典

- 同じ試行の `sim_step` とフレームの `buffer_index`、既存エンコーダーの30fpsを使い、フレーム間は補間します。モデルの待ち時間をMP4の時間へ換算しません。
- `video_combined.mp4` は記録されたメインバッファのカメラ、`video_combined_wrist.mp4` は手先のバッファのカメラに対応付けます。`video_combined_<key>.mp4` は、記録器と同じ方法で安全な名前に変換した `<key>` のカメラが記録されていれば、そのカメラに対応付けます。runner出力にもこの3種類の名前を使えます。
- 選んだ動画のカメラのフレームを使って同期します。そのカメラに使えるフレームがない場合に限り、ほかのカメラのフレーム番号とstepの対応がすべて同一なら代用します。一部だけあるフレームを別カメラで補完しません。epoch 0、先頭buffer index 0、単調なstep、末尾と動画長の整合が必要です。環境リセット、不十分・矛盾する情報では「同期情報なし」と表示します。
- 全カメラ表示ではメイン以外の動画をミュートし、再生・停止・位置・速度をメインの動画に揃えます。カメラ名は正面・手先・頭・左右手首などの短いラベルで表示し、元の名前はカーソルを重ねて確認できます。未知のカメラ名は元の名前のまま表示します。
- 候補自身にsim_stepがなくても、同じ記録ターンに一意な統合イベントがあれば、その位置を参照したことを明記してまとめます。候補自身の処理時刻を測れたことは意味しません。
- 候補数は記録に従い、参照設定の9件へ水増ししません。HTTP再試行は一つの論理呼び出し内へまとめます。
- 正規化済みpayloadの候補区間にtemperatureと回答全文が一意に一致した場合だけ、統合への送信を確認済みと表示します。最終回答へのアイデアの採用率は示しません。
- `FINISH`はモデルの主張、stdoutの成功文は実行コードの申告、reward/task_completedは評価器・ハーネスの値として出典を分けます。
- 旧形式の保存ログで実送信payloadやマスクが欠けていれば未記録と表示します。保存プロンプト、見た目が似た画像、前後の試行から実入力を補いません。

動画位置を特定できない処理も一覧に「同期なし」と表示します。行を選ぶと入出力が開き、動画は現在位置で停止します。

## 必要な記録

| 確認する内容 | 同じ試行で必要な記録 |
|---|---|
| 録画と処理の同期 | MP4、イベント、フレーム番号とsim_step、camera・epoch・turn_index |
| SAM3 | 実送信画像・対象指示、返却マスク、要求と応答のID |
| VDM | 実送信payload、比較画像の送信順、返された説明 |
| コード生成・候補 | 実送信payload、回答、temperature、エラー・finish_reason |
| 統合 | 実送信payload、最終回答、候補IDと実行コードへの参照 |
| Python実行 | 実行コード、stdout/stderr、コードブロックID、APIイベント |
| APIと呼び出し行 | `api_call_start.call_site.code_block_id` / `line`、参照先の `code_block_start.code`、`api_call_end` / `api_call_error` |
| APIからモデル入出力 | 実行ブロックの `source_model_event_id`、対応するモデル回答・HTTP要求と実送信payload |

記録器の導入方法は[上流README](upstream-readme.md#recording-traces)を参照してください。viewerを導入するだけでは、過去の未保存データは増えません。

## 検証

[READMEの検証手順](../README.md#検証)で再現できます。合成デモでは「再生→停止→ログ選択→入出力→候補→統合結果」、同位置イベント、MP4のみ、狭幅、動きを減らす設定を確認しています。

複数カメラの合成デモは `python scripts/make_replay_demo.py --out outputs/multi_camera_demo --cameras 3` で作成できます。`--cameras 2` は正面と手先、`--cameras 3` は頭と左右の手首の録画です。各出力先は新しいディレクトリを指定してください。起動済みのviewerには `python scripts/demo/check_multi_camera.py --fixture outputs/multi_camera_demo --base-url http://127.0.0.1:8390` で、3台の表示、再生位置のずれ、カメラ切り替え、API一覧の追従を確認できます。CIでも3台のデモを生成して同じ確認を実行します。

複数カメラの動画名・カメラ対応・同期の安全条件と、カメラ切り替え・位置保持・要約・比較・停止原因の画面テストは `cd web-ui && npm run test:trace` で実行できます。`scripts/test-trace.mjs` が Node のテストランナーで実行します。

同じブラウザ検証スクリプトに「APIとPython」の操作も含みます。`goto_pose`と3行目、同時刻の3 API、スライダーとEndキーのシーク、ホバー前後の選択・時刻、コード前後移動、生成元モデルの入出力、候補・統合結果、再生追従を確認します。

GMOでトレースを記録した `two_arm_handover`（seed 301、Oracle）をChromeで検証しました。11.30秒で `close_gripper_arm1` の34行目を表示し、Endキーで動画の終端に移動します。0.00秒の `get_hammer_pose` と `open_gripper_arm0` は4行目と20行目を個別に選べます。
